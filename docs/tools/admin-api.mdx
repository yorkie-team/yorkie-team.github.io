## Admin API

The Yorkie Admin API allows developers to interact programmatically with their Yorkie documents without using the Yorkie SDK. It is convenient for managing documents in server-side applications.

The API is implemented using [Connect protocol](https://connectrpc.com/docs/protocol/), which means all requests are made using HTTP POST method to a specific service endpoint. The API accepts JSON-encoded request bodies, returns JSON-encoded responses, and uses standard HTTP response codes.

**Base URL**: `{{API_ADDR}}/yorkie.v1.AdminService/`

Requests accept field names in either `snake_case` or `lowerCamelCase`. Responses use the standard Protobuf JSON mapping: field names are `lowerCamelCase`, 64-bit integers are strings, `bytes` fields are base64 strings, timestamps are RFC 3339 strings, and fields with default values (such as `0`, `false` or an empty string) are omitted.

### Authentication

The Admin API accepts two credentials: a project's secret key with the `API-Key` scheme, and a login token with the `Bearer` scheme. Which ones a request may use depends on the endpoint:

- **Project-scoped endpoints** work on a single project. These are `GetProjectStats`, the document endpoints (`CreateDocument`, `ListDocuments`, `GetDocument`, `GetDocuments`, `SearchDocuments`, `UpdateDocument`, `RemoveDocumentByAdmin`, `CompactDocumentByAdmin`, `GetSnapshotMeta`, `ListChanges`), the schema endpoints (`CreateSchema`, `ListSchemas`, `GetSchema`, `GetSchemas`, `RemoveSchema`), the channel endpoints (`ListChannels`, `GetChannels`, `BroadcastByAdmin`), and `RevalidateAccess`. Every endpoint on this page is project-scoped, except `UpdateProject` in [Project Management](#project-management). They accept either credential:
  - The project's **secret key**, which carries the authority of a project admin and can call all of these endpoints. Keep it on your server and never ship it in client-side code.
  - A **login token** together with an `x-yorkie-project` header that names the project. The request is checked against your role in that project: endpoints that change the project (`CreateDocument`, `UpdateDocument`, `RemoveDocumentByAdmin`, `CompactDocumentByAdmin`, `CreateSchema`, `RemoveSchema`, `BroadcastByAdmin`, `RevalidateAccess`) need the `admin` or `owner` role, and the other, read-only endpoints are open to every member of the project.
- **User-scoped endpoints** are every other authenticated endpoint, such as `ListProjects`, `CreateProject`, `GetProject`, `UpdateProject`, `RotateProjectKeys`, the member and invite endpoints, and the revision endpoints (`ListRevisionsByAdmin`, `GetRevisionByAdmin`, `RestoreRevisionByAdmin`). They act as a user account, and accept only a login token. `GetProject` and `ListProjects` return a project's secret key only to its `admin` and `owner` members; for the `member` role, `secret_key` is empty.

Wherever a login token is accepted and the request has no `authorization` header, the `yorkie_session` cookie, which the server sets when you sign in to the Dashboard, is used as the token instead.

`LogIn`, `SignUp`, `ChangePassword` and `DeleteAccount` take no authorization header: `ChangePassword` and `DeleteAccount` check the username and password in the request body instead. `GetServerVersion` needs a valid credential, and accepts either scheme.

A project-scoped endpoint can take the secret key with the `API-Key` scheme:

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/ListDocuments' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{"page_size": 10}'
```

A login token comes from `LogIn`. A user-scoped endpoint takes it alone:

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/LogIn' \
  -H 'content-type: application/json' \
  --data-raw '{"username": "USERNAME", "password": "PASSWORD"}'
# {"token":"TOKEN"}

curl '{{API_ADDR}}/yorkie.v1.AdminService/ListProjects' \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer TOKEN' \
  --data-raw '{}'
```

A project-scoped endpoint takes it with the project name:

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/ListDocuments' \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer TOKEN' \
  -H 'x-yorkie-project: PROJECT_NAME' \
  --data-raw '{"page_size": 10}'
```

These requests fail with `permission_denied`:

- A credential the endpoint does not accept, such as a secret key on `ListProjects`, or a token without the `x-yorkie-project` header on `ListDocuments`.
- A token whose user's role in the named project is too low for the endpoint, or whose user is not a member of it. A project that does not exist answers the same way, so the header cannot be used to find out which project names exist.

A request with no credential, an empty or blank secret key, or a key or token the server does not recognize fails with `unauthenticated`.

### Documents Management

#### POST /yorkie.v1.AdminService/CreateDocument

This endpoint creates a new document in the specified project. If `initial_root` is provided, it is used as the initial content of the document. Otherwise, an empty document is created.

##### Request

Parameters:

- `document_key`: A unique key for the new document.
- `initial_root`: The initial root([YSON string](/docs/internals/yson)) of the document.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/CreateDocument' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "document_key": "document-1",
    "initial_root": "{\"type\":\"doc\",\"content\":[]}"
  }'
```

##### Response

```json
{
  "document": {
    "id": "686e2aa9666f9626c2d62cb4",
    "key": "document-1",
    "root": "{\"content\":[],\"type\":\"doc\"}",
    "documentSize": {
      "live": { "data": 6, "meta": 96 },
      "gc": {}
    },
    "createdAt": "2025-05-12T10:00:00Z",
    "accessedAt": "2025-05-12T10:00:00Z",
    "updatedAt": "2025-05-12T10:00:00Z"
  }
}
```

#### POST /yorkie.v1.AdminService/UpdateDocument

This endpoint updates the content of an existing document, the [schema](/docs/advanced/schema-validation) bound to it, or both.

##### Request

Parameters:

- `document_key`: The key of the document to update.
- `root`: The new root content ([YSON string](/docs/internals/yson)) of the document.
- `schema_key`: The schema to bind to the document, in the form `name@version`.

Which fields you set decides what the request does:

| `root` | `schema_key` | Result |
|--------|--------------|--------|
| set | empty | Replaces the root. The new root is validated against the schema already bound to the document, if any |
| empty | set | Binds the document to the given schema. The current root must conform to it |
| set | set | Replaces the root and binds the schema. The new root must conform to it |
| empty | empty | Removes the schema binding from the document |

Every request except a root-only update fails with `ErrDocumentAttached` while any client is attached to the document. Note that a request with neither field set is not a no-op: it detaches the document's schema.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/UpdateDocument' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "document_key": "document-1",
    "root": "{\"type\":\"doc\",\"content\":[{\"type\":\"paragraph\",\"content\":[{\"text\":\"Updated content\",\"type\":\"text\"}]}]}"
  }'
```

##### Response

```json
{
  "document": {
    "id": "686e2aa9666f9626c2d62cb4",
    "key": "document-1",
    "root": "{\"content\":[{\"content\":[{\"text\":\"Updated content\",\"type\":\"text\"}],\"type\":\"paragraph\"}],\"type\":\"doc\"}",
    "createdAt": "2025-03-24T12:00:00Z",
    "accessedAt": "2025-05-12T11:30:00Z",
    "updatedAt": "2025-05-12T11:30:00Z"
  }
}
```

#### POST /yorkie.v1.AdminService/ListDocuments

This endpoint returns a list of documents in a project. A pagination mechanism allows you to retrieve documents in batches. Provide the `previous_id` of the last document in the previous page to get the next page of documents.

To include the root of each document in the response, set the `include_root` parameter to `true`.

##### Request

Parameters:
- `previous_id`: The ID of the last document in the previous page. If not provided, the first page will be returned.
- `page_size`: The number of documents to return.
- `is_forward`: Whether to return documents in ascending order.
- `include_root`: Whether to include root in the response.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/ListDocuments' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "previous_id": "686e2aa9666f9626c2d62cb4",
    "page_size": 20,
    "is_forward": true,
    "include_root": false
  }'
```

##### Response
```json
{
  "documents": [
    {
      "id": "686e2aa9666f9626c2d62cb5",
      "key": "document-2",
      "attachedClients": 2,
      "createdAt": "2025-03-24T12:00:00Z",
      "accessedAt": "2025-03-24T13:00:00Z",
      "updatedAt": "2025-03-24T13:00:00Z"
    },
    {
      "id": "686e2aa9666f9626c2d62cb6",
      "key": "document-3",
      "createdAt": "2025-03-25T10:00:00Z",
      "accessedAt": "2025-03-25T10:00:00Z",
      "updatedAt": "2025-03-25T09:30:00Z"
    }
  ]
}
```

`root` is included only when `include_root` is `true`.

#### POST /yorkie.v1.AdminService/ListChanges

List the changes stored for a document, page by page, by server sequence.

##### Request

Parameters:
- `document_key`: The key of the document.
- `previous_seq`: The server sequence to page from. The page starts after it when `is_forward` is `true`, and before it otherwise. Use `0` to start from the first change (forward) or the latest change (backward).
- `page_size`: The number of changes to return.
- `is_forward`: Whether to page toward newer changes.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/ListChanges' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "document_key": "document-1",
    "previous_seq": 0,
    "page_size": 10,
    "is_forward": false
  }'
```

##### Response

`changes` is a list of `Change` messages as defined in [`resources.proto`](https://github.com/yorkie-team/yorkie/blob/main/api/yorkie/v1/resources.proto), each with its `id`, `message`, `operations` and `presenceChange`.

#### POST /yorkie.v1.AdminService/CompactDocumentByAdmin

Compact a document's change history. Yorkie rebuilds the document from its latest state as a single initial change and replaces the stored change history with it. The document's content does not change, and the request fails if the rebuilt content would differ.

##### Request

Parameters:
- `document_key`: The key of the document.
- `force`: Whether to compact the document even if clients are attached to it.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/CompactDocumentByAdmin' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "document_key": "document-1",
    "force": false
  }'
```

##### Response

`compacted` is `true` when the document was compacted. Without `force`, a document that is attached to any client is left as is, and the response has no `compacted` field (it is `false`).

```json
{
  "compacted": true
}
```

### Channel Management

#### POST /yorkie.v1.AdminService/ListChannels

List the active channels of the project, with the session count of each.

##### Request

Parameters:

- `query`: A channel key prefix. Only channels whose keys start with it are returned. When empty, all channels are listed.
- `limit`: The maximum number of channels to return, from `1` to `100`. A value outside this range fails with `invalid_argument`.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/ListChannels' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "query": "room-1",
    "limit": 20
  }'
```

##### Response

```json
{
  "channels": [
    {
      "key": "room-1",
      "sessionCount": 10
    },
    {
      "key": "room-1.section-1",
      "sessionCount": 20
    }
  ]
}
```

#### POST /yorkie.v1.AdminService/GetChannels

This endpoint retrieves channel information without requiring an SDK client to attach to the channels. It returns the session count (the number of connected clients) for the specified channels.

Channels support [hierarchical keys using periods (`.`) as separators](/docs/sdks/js-sdk#hierarchical-channel-keys). When `include_sub_path` is enabled, the session count includes all clients connected to sub-level channels.

##### Request

Parameters:

- `channel_keys`: An array of channel keys to retrieve information for.
- `include_sub_path`: Whether to include session counts from sub-level channels in the total count.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/GetChannels' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "channel_keys": ["room-1", "room-1.section-1"],
    "include_sub_path": false
  }'
```

##### Response

If `room-1` has 10 direct connections and `room-1.section-1` has 20 connections, the response would be:

**Case 1: Get exact channel session counts (`include_sub_path: false`)**

When `include_sub_path` is `false`, the `sessionCount` for a channel includes only the direct connections to that channel.
In this case, the session count for `room-1` would be 10 and the session count for `room-1.section-1` would be 20.

```json
{
  "channels": [
    {
      "key": "room-1",
      "sessionCount": 10
    },
    {
      "key": "room-1.section-1",
      "sessionCount": 20
    }
  ]
}
```

**Case 2: Get channel session counts including sub-levels (`include_sub_path: true`)**

When `include_sub_path` is `true`, the `sessionCount` for a channel includes all clients connected to that channel and any sub-level channels. 
In this case, the total session count for `room-1` would include both 10 and 20, totaling 30.

```json
{
  "channels": [
    {
      "key": "room-1",
      "sessionCount": 30
    },
    {
      "key": "room-1.section-1",
      "sessionCount": 20
    }
  ]
}
```

#### POST /yorkie.v1.AdminService/BroadcastByAdmin

Broadcast a message to the clients attached to a channel, as [`channel.broadcast`](/docs/sdks/js-sdk#channel) does from an SDK client.

##### Request

Parameters:

- `channel_key`: The key of the channel.
- `topic`: The topic of the message. Clients receive it through `channel.subscribe(topic, callback)`.
- `payload`: The message, as a base64 string. The JS SDK decodes the payload as UTF-8 JSON, so encode a JSON value. For example, `eyJtZXNzYWdlIjoiaGVsbG8ifQ==` is `{"message":"hello"}`.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/BroadcastByAdmin' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "channel_key": "room-1",
    "topic": "notice",
    "payload": "eyJtZXNzYWdlIjoiaGVsbG8ifQ=="
  }'
```

##### Response
Empty response with success status code.

### Access Management

#### POST /yorkie.v1.AdminService/RevalidateAccess

This endpoint asks Yorkie to verify again the authorization of the project's open `Watch` streams after a permission changes in your system. On every Yorkie server, it drops the project's cached [Auth Webhook](/docs/advanced/security#auth-webhook) decisions about the given keys, then asks the webhook again for each open `Watch` stream that watches any of them. A stream the webhook now denies is closed; streams it still allows keep running. See [Applying Permission Changes](/docs/advanced/security#applying-permission-changes).

##### Request

Parameters:

- `keys`: The document or channel keys whose access changed, up to 1000. Keys match exactly: a channel key does not cover its sub-level channels. When empty, every open stream of the project is re-checked and all of its cached decisions are dropped.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/RevalidateAccess' \
  -H 'content-type: application/json' \
  -H 'authorization: API-Key PROJECT_SECRET_KEY' \
  --data-raw '{
    "keys": ["document-1", "room-1"]
  }'
```

##### Response

`closedStreams` is the number of streams closed across all servers.

```json
{
  "closedStreams": 2
}
```

If the webhook could not be reached for some streams, those streams are left open and the request fails with `unavailable` (`ErrRevalidationIncomplete`). Retry the whole request.

### Project Management

#### POST /yorkie.v1.AdminService/UpdateProject

Update the settings of a project. This is a user-scoped endpoint: it takes a login token with the `Bearer` scheme, not the secret key, and needs the `admin` or `owner` role in the project. Some settings, such as `max_size_per_document` and `auto_revision_enabled`, have no CLI flag and are set through this endpoint or the Dashboard. See [Resources](/docs/advanced/resources) for what each setting does.

##### Request

Parameters:

- `id`: The ID of the project, as returned by `GetProject` or `yorkie project ls --output json`.
- `fields`: The settings to change. Fields you leave out keep their current values. The available fields are `name`, `auth_webhook_url`, `auth_webhook_methods` (`{"methods": [...]}`), `auth_webhook_max_retries`, `auth_webhook_min_wait_interval`, `auth_webhook_max_wait_interval`, `auth_webhook_request_timeout`, `event_webhook_url`, `event_webhook_events` (`{"events": [...]}`), `event_webhook_max_retries`, `event_webhook_min_wait_interval`, `event_webhook_max_wait_interval`, `event_webhook_request_timeout`, `snapshot_threshold`, `snapshot_interval`, `client_deactivate_threshold`, `max_subscribers_per_document`, `max_attachments_per_document`, `max_size_per_document`, `remove_on_detach`, `auto_revision_enabled`, `channel_session_ttl`, `channel_batch_window` and `allowed_origins` (`{"origins": [...]}`). Durations are Go duration strings such as `"100ms"` or `"24h"`.

```bash
curl '{{API_ADDR}}/yorkie.v1.AdminService/UpdateProject' \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer TOKEN' \
  --data-raw '{
    "id": "6ac32edca4736914b08f6be3",
    "fields": {
      "max_size_per_document": 5242880,
      "auto_revision_enabled": false
    }
  }'
```

##### Response

The response has the updated `project`, with the same fields as `GetProject`.
