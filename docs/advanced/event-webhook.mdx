## Event Webhook

The Event Webhook allows you to receive notifications when specific events occur in your Yorkie documents. Unlike the [Auth Webhook](/docs/advanced/security#auth-webhook) which handles authorization, the Event Webhook is designed for integrations and notifications when document state changes.

### How It Works

When a configured event occurs, Yorkie sends an HTTP POST request to your webhook endpoint with details about the event.

<Mermaid
  chart={`sequenceDiagram
    participant Client
    participant Server as Yorkie Server
    participant Webhook as Your Webhook Server

    Client->>Server: (1) Edit document
    Server->>Server: (2) Process changes

1. A client makes changes to a document
2. Yorkie server processes the changes
3. If the event matches configured triggers, Yorkie sends a webhook request
4. Your server processes the event (e.g., send notifications, update external systems)
5. Your server responds to acknowledge receipt

### Supported Events

| Event | Description |
|-------|-------------|
| `DocumentRootChanged` | Triggered after the server stores a pushed change that contains operations on the document's root. Presence-only updates do not trigger it |

### Rate Limiting

Yorkie does not send one request per change. Events are throttled per document and event type with a 1-second window:

- The first event for a document is sent immediately.
- Further events within the next second are not sent individually. Yorkie keeps only the latest one.
- After the burst settles, Yorkie sends one trailing request for the suppressed events.

A burst of edits therefore produces at most about one webhook request per second for each document, plus a final request after the burst ends. Treat each request as a signal that the document changed, and read the latest content from Yorkie (for example, through the [Admin API](/docs/tools/admin-api)) if you need it.

### Setup and Configuration

#### 1. Configure the Event Webhook

You can configure the Event Webhook using the Yorkie CLI:

```bash
# Set the webhook URL and enable the DocumentRootChanged event
yorkie project update [project-name] \
  --event-webhook-url "https://your-server.com/webhook" \
  --event-webhook-events-add "DocumentRootChanged"
```

To disable specific events:

```bash
yorkie project update [project-name] \
  --event-webhook-events-rm "DocumentRootChanged"
```

To enable all events:

```bash
yorkie project update [project-name] \
  --event-webhook-events-add "ALL"
```

#### 2. Webhook Request Format

When an event is triggered, Yorkie sends a POST request with the following JSON payload:

```json
{
  "type": "DocumentRootChanged",
  "attributes": {
    "key": "your-document-key",
    "issuedAt": "2025-01-02T15:04:05.000Z"
  }
}
```

| Field | Description |
|-------|-------------|
| `type` | The event type that triggered the webhook |
| `attributes.key` | The key of the document that triggered the event |
| `attributes.issuedAt` | ISO 8601 timestamp when the event occurred |

Each request carries these headers:

| Header | Description |
|--------|-------------|
| `Content-Type` | `application/json` |
| `X-Signature-256` | `sha256=` followed by the hex-encoded HMAC-SHA256 of the raw request body, keyed by the project's secret key |

See [Verifying Requests](#verifying-requests) for how to check the signature.

#### 3. Webhook Response

Your webhook server should respond with an HTTP status code:

| Status Code | Meaning |
|-------------|---------|
| `200 OK` | Event received and processed successfully |
| `500`, `503`, `504`, `429` | Yorkie retries the request based on the [retry configuration](#retry-configuration) |
| Any other status | The delivery fails without a retry, and the server logs the error |

Yorkie also retries when the connection is reset before a response arrives. Other failures, such as a request timeout or a `400`, `404` or `502` response, are not retried, so the event is dropped. Return one of the retryable status codes if you want Yorkie to try again later.

### Retry Configuration

The Event Webhook includes configurable retry behavior with exponential backoff for failed requests. Before retry `n` (starting at 0), Yorkie waits `min(2^n × min-wait-interval, max-wait-interval)`. With `max-retries` set to 10, a request is attempted up to 11 times.

| Setting | Default | Description |
|---------|---------|-------------|
| `event-webhook-max-retries` | 10 | Maximum number of retry attempts |
| `event-webhook-min-wait-interval` | 100ms | Minimum wait time between retries |
| `event-webhook-max-wait-interval` | 3s | Maximum wait time between retries |
| `event-webhook-request-timeout` | 3s | Timeout for each webhook request |

#### Configure Retry Settings

```bash
yorkie project update [project-name] \
  --event-webhook-max-retries 5 \
  --event-webhook-min-wait-interval 200ms \
  --event-webhook-max-wait-interval 5s \
  --event-webhook-request-timeout 10s
```

### Verifying Requests

Yorkie signs every event webhook request with the project's secret key. To confirm that a request came from your Yorkie project, compute the HMAC-SHA256 of the raw request body with the secret key and compare it with the `X-Signature-256` header.

Compute the signature over the raw bytes you received. A body that has been parsed and serialized again (for example, by `express.json()`) may differ from what Yorkie signed.

```javascript
const crypto = require('crypto');
const express = require('express');
const app = express();

const SECRET_KEY = process.env.YORKIE_SECRET_KEY;

app.post('/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const expected =
    'sha256=' +
    crypto.createHmac('sha256', SECRET_KEY).update(req.body).digest('hex');
  const received = req.get('X-Signature-256') || '';

  if (
    received.length !== expected.length ||
    !crypto.timingSafeEqual(Buffer.from(received), Buffer.from(expected))
  ) {
    return res.status(401).send('Invalid signature');
  }

  const { type, attributes } = JSON.parse(req.body.toString('utf8'));
  console.log(`Event: ${type}, Document: ${attributes.key}`);

  res.status(200).send('OK');
});
```

<Alert status="warning">
The signing key is the project's secret key. If you rotate the project's keys, update the key your webhook server uses to verify requests. See [API Keys](/docs/advanced/projects#api-keys) for details on project keys.
</Alert>

### Example Webhook Server

Here's a simple example of an Express.js webhook server:

```javascript
const express = require('express');
const app = express();

app.use(express.json());

app.post('/webhook', (req, res) => {
  const { type, attributes } = req.body;

  console.log(`Event: ${type}`);
  console.log(`Document: ${attributes.key}`);
  console.log(`Time: ${attributes.issuedAt}`);

  // Process the event (e.g., send notifications, update cache)

  res.status(200).send('OK');
});

app.listen(3000, () => {
  console.log('Webhook server listening on port 3000');
});
```

### Use Cases

- **Real-time notifications**: Notify users when a shared document is updated
- **External system sync**: Keep external databases or services in sync with document changes
- **Audit logging**: Record document change events for compliance
- **Cache invalidation**: Invalidate caches when documents change
